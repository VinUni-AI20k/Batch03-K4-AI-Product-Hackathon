## 1. Phần việc mình phụ trách

Mình phụ trách mảng Tích hợp & Vận hành (Integration & Operations) của dự án. Công việc chính của mình là kết nối các module độc lập từ các thành viên khác thành một luồng xử lý trọn vẹn (end-to-end pipeline), xây dựng API backend cho Frontend gọi dữ liệu, thiết lập cơ chế xử lý lỗi/retry/fallback cache để đảm bảo hệ thống hoạt động ổn định và đóng gói toàn bộ ứng dụng bằng Docker để sẵn sàng triển khai.

Các phần việc cụ thể mình đã thực hiện trong repo bao gồm:

- **PDF upload & outline extraction:**
  - Xây dựng endpoint `/api/knowledge/upload` trong [`backend/app/api/routes_upload.py`](../backend/app/api/routes_upload.py) nhận file slide PDF từ frontend, trích xuất text và lưu thông tin outline của slides.
- **Transcript upload & mapping data:**
  - Xử lý nhận file transcript (.md, .txt, .vtt, .srt) qua API.
  - Phối hợp cùng Linh (D) để chạy pipeline phân loại transcript (Classify Segment) và align các slide với transcript dựa trên mã đoạn `[Txx-NNN]`.
  - Xử lý các case biên đặc thù: Nếu chỉ tải PDF -> tự động dùng demo transcript làm nguồn; nếu chỉ tải transcript -> transcript tự đóng vai trò outline (không cần slide).
- **Tính năng tóm tắt dữ liệu (Summarize Card) & Ví dụ thực tiễn (Practical Examples):**
  - Tích hợp pipeline sinh Study Note (`/api/reteach/study-note`) cung cấp tóm tắt chi tiết cho từng phần học sinh bị yếu dựa trên prompt/model rewrite của Mai Anh (B).
  - Viết endpoint sinh ví dụ thực tế `/api/reteach/examples` trong [`backend/app/api/routes_reteach.py`](../backend/app/api/routes_reteach.py), dùng LLM (OpenAI API qua `call_json`) để tự động tạo các ví dụ minh họa trực quan, dễ hiểu bằng tiếng Việt cho từng section tương ứng với nội dung tóm tắt để hiển thị lên UI.
- **Error handling, Retry & Fallback cache:**
  - Viết cơ chế xoay vòng API keys (multiple OpenAI/Gemini keys) và tự động retry 1 lần khi có lỗi mạng (5xx, 429) trong [`backend/app/core/llm_client_openai.py`](../backend/app/core/llm_client_openai.py).
  - Lưu trữ kết quả chạy thành công của bộ demo vào file cache dự phòng. Khi hệ thống gặp lỗi LLM không thể phục hồi hoặc mất mạng đột ngột, API sẽ tự động chuyển sang đọc dữ liệu từ cache để đảm bảo demo offline trơn tru.
- **Deploy web với Docker (Multi-stage build):**
  - Xây dựng [`Dockerfile`](../Dockerfile) dạng multi-stage build:
    - Stage 1: Build frontend React/Vite/TS bằng Node.
    - Stage 2: Cài đặt dependencies cho backend python (FastAPI).
    - Stage 3 (Final): Gom kết quả build frontend vào thư mục Nginx static public, cài đặt Nginx và Supervisor để quản lý đồng thời hai process (FastAPI chạy ở port 8000 và Nginx lắng nghe ở port 80, proxy toàn bộ requests `/api` và `/docs` tới backend).
  - Cấu hình port, CORS, và các biến môi trường thống nhất để chạy một lệnh `docker build` là có thể chạy cả app hoàn chỉnh.

## 2. AI đã hỗ trợ mình như thế nào

AI đã giúp mình tiết kiệm rất nhiều thời gian trong các việc sau:
- Gợi ý cấu trúc [`Dockerfile`](../Dockerfile) tối ưu và cấu hình Supervisor để chạy đa dịch vụ (Nginx + FastAPI) trong cùng một container một cách ổn định, tránh việc phải tạo nhiều container riêng lẻ khó quản lý mạng trong thời gian hackathon ngắn.
- Viết nhanh các đoạn code cấu hình Nginx proxy pass chính xác cho các đường dẫn `/api` và `/docs`.
- Hỗ trợ xây dựng khung prompt cho `SYSTEM_EXAMPLE_PROMPT` nhằm sinh ra ví dụ tiếng Việt tự nhiên và ép kiểu JSON đầu ra để frontend parse dễ dàng.

Tuy nhiên, AI không thể tự chạy thử để kiểm thử kết nối mạng thực tế. Mình phải tự debug các lỗi liên quan đến CORS (giữa port 5173 và 8000), sửa lỗi proxy khi chạy Docker trên các môi trường máy chủ khác nhau, và thiết kế kịch bản fallback cache sao cho logic nghiệp vụ không bị gián đoạn.

## 3. Một case fail và bài học

Một case fail lớn trong quá trình tích hợp là latency của pipeline sinh Study Note ở Checkpoint 1. Lúc đầu, luồng API gọi LLM sinh Study Note rồi sau đó gọi tuần tự thêm một loạt API calls để sinh ví dụ thực tế cho 3 section yếu cùng lúc. Tổng thời gian phản hồi (latency) lên tới hơn 40 giây, khiến frontend bị timeout hoặc người dùng tưởng ứng dụng bị đơ (nạn nhân của lỗi số 9 trong bảng 8 lớp lỗi ở spec).

**Nguyên nhân:** Gọi LLM sinh ví dụ một cách tuần tự (sequential) cho từng section yếu, cộng thêm việc sinh Study Note của Mai Anh (B) vốn đã tốn thời gian.
**Bài học & Giải quyết:** Mình đã chuyển phần sinh ví dụ (`/examples`) thành một API riêng biệt gọi song song hoặc gọi sau khi Study Note đã render phần thô. Đồng thời đề xuất phía Trà (C) làm UI loading spinner trạng thái chi tiết theo từng bước (đang tải slides -> đang align -> đang viết bài học -> đang sinh ví dụ...) và hướng dẫn Mai Anh (B) giới hạn độ dài Study Note ngắn gọn khi nguồn mỏng.

## 4. Điều mình làm tốt và cần cải thiện

**Điều mình làm tốt:**
- Đóng gói Docker chạy rất mượt mà. Việc dùng Supervisor chạy chung Nginx và Backend trong 1 container giúp quá trình chạy demo cực kỳ đơn giản (chỉ cần chạy docker run và mở port 80 là dùng được ngay).
- Cơ chế fallback cache hoạt động hoàn hảo: Mình đã lưu sẵn 3 kịch bản quiz sai cố ý và các Study Note tương ứng. Khi test ngắt kết nối mạng giả lập, hệ thống vẫn trả về bài học và retest tương ứng từ cache, giúp team tự tin 100% khi đi thuyết trình demo không lo nghẽn mạng hay API rate limit.

**Điều cần cải thiện:**
- Việc quản lý session ID hiện đang lưu hoàn toàn trong bộ nhớ/sqlite tạm thời trên local. Khi container Docker bị khởi động lại, các session cũ sẽ bị mất sạch. Nếu có thêm thời gian, mình nên tích hợp một cơ chế lưu session bền vững hơn (ví dụ lưu file JSON có cấu trúc trên volume ngoài hoặc SQLite thực tế lưu trên host).
- Cần tối ưu thêm việc streaming nội dung bài giảng để tăng trải nghiệm người dùng, thay vì chờ toàn bộ Study Note sinh xong mới trả về cho frontend.
